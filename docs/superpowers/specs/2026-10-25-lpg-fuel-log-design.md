# LPG Fuel Log — แบบโปรเจกต์ฉบับเสนอ

วันที่: 25 ตุลาคม 2026
สถานะ: รอผู้ใช้ตรวจแบบก่อนเขียนแผนและเริ่มพัฒนา

## 1. เป้าหมายและบริบท

ทำเว็บบันทึกการเติม LPG ให้พ่อของผู้ใช้ ใช้กับรถหนึ่งคันและมือถือหนึ่งเครื่องเป็นหลัก พ่อเปิดจากไอคอนแล้วใช้งานได้โดยไม่กรอกบัญชีหรือรหัสผ่าน ผู้ใช้เป็นผู้ตั้งค่าและดูแลระบบให้ครั้งแรก

อีกเป้าหมายคือให้ผู้ใช้ทบทวน JavaScript ฝึก React, REST API และ PostgreSQL ผ่านผลงาน Full-stack ที่ใช้จริง ผู้ใช้เลือก React + Node.js/Express + PostgreSQL แล้ว การพัฒนาในอนาคตจะทำเป็นส่วนสั้นที่ทดลองได้ พร้อมคำอธิบายและกิจกรรมให้ผู้ใช้ลองแก้โค้ด

## 2. สิ่งที่ผู้ใช้ระบุ และข้อเสนอของผู้ออกแบบ

**ผู้ใช้ระบุ:** พ่อใช้คนเดียว มือถือเครื่องเดียว รถใช้ LPG ต้องใช้ง่าย ไม่ต้องล็อกอินซ้ำ ต้องการฝึกและนำผลงานไปสมัครงาน โดยสนใจ Full-stack มากกว่า Frontend

**ข้อเสนอที่ยังตรวจแก้ได้ในเอกสารนี้:** ใช้ภาษาไทย เงินบาท กิโลเมตร ลิตร และวันตาม Asia/Bangkok; ไม่บังคับเลขไมล์; กรอกเฉพาะวันที่โดยไม่บังคับเวลา; ใช้ JavaScript กับ CSS ธรรมดา; หน้าหลักเริ่มที่ฟอร์ม; จำสิทธิ์เครื่องด้วย cookie หลังตั้งค่าผ่านลิงก์ส่วนตัว; ลบแบบเก็บรายการไว้เบื้องหลังเพื่อกู้ด้วยเครื่องมือผู้ดูแลได้

## 3. Approaches — วิธีที่พิจารณา

| วิธี | ข้อดีสำหรับโครงการ | สิ่งที่แลก |
|---|---|---|
| React + Supabase Data API | เชื่อมข้อมูลได้เร็ว ฝึก React และ SQL | ได้ฝึกเขียน HTTP API และ Backend เองน้อยกว่า |
| React + Node.js/Express + PostgreSQL | เห็นเส้นทางข้อมูลครบ ออกแบบ API และ SQL เอง มีหลักฐานงาน Full-stack | ต้องดูแล Backend การเผยแพร่ และการเข้าถึงข้อมูลเพิ่ม |

ผู้ใช้เลือกแบบที่สอง หลังจากคุยเรื่องเวลา เป้าหมายการเรียนรู้ และความง่ายสำหรับพ่อ ส่วน Google Sheets + Apps Script ที่เคยเสนอในแชตเก่าไม่ใช่แนวทางที่เลือกสำหรับเป้าหมายปัจจุบัน

## 4. ขอบเขตรุ่นแรก

- เพิ่มรายการเติม LPG พร้อมวันที่ จำนวนเงิน ลิตร และข้อมูลเสริม
- ดูประวัติเรียงวันที่เติมล่าสุดก่อน กรองตามเดือน และโหลดเพิ่มได้
- แก้ไขรายการ และยืนยันก่อนลบ
- ดูยอดเงิน จำนวนลิตร จำนวนครั้ง และราคาเฉลี่ยถ่วงน้ำหนักของเดือนที่เลือก
- เก็บแบบร่างบนเครื่องเมื่อส่งไม่สำเร็จ และป้องกันการเพิ่มซ้ำเมื่อส่งใหม่
- ตั้งค่าการเข้าใช้หนึ่งครั้งโดยผู้ใช้ จากนั้นพ่อเปิดใช้ได้โดยไม่ล็อกอิน
- มีคำอธิบายระบบ วิธีรัน การทดสอบ วิธีสำรอง/กู้คืน และภาพตัวอย่างสำหรับ Portfolio

ยังไม่ทำ: สมัครสมาชิก บทบาท Admin/User รถหลายคัน เชื่อมปั๊ม OCR ใบเสร็จ ตำแหน่ง GPS การซิงก์ออฟไลน์อัตโนมัติ และการคำนวณ กม./ลิตร กราฟไม่ใช่เงื่อนไขสำเร็จของรุ่นแรก

สิ่งที่ถือว่าล้มเหลวแม้ระบบเปิดได้: พ่อต้องจำรหัส, แสดงว่าสำเร็จก่อนฐานข้อมูลยืนยัน, ส่งใหม่แล้วเกิดรายการซ้ำ, เน็ตหลุดแล้วฟอร์มหาย, ตัวหนังสือเล็กหรือขั้นตอนที่พ่อใช้ไม่สะดวก, หรือผู้ใช้ไม่เข้าใจโค้ดส่วนสำคัญที่นำไปเล่าใน CV

## 5. โครงสร้างระบบและการพัฒนา

- React + Vite: components, state, form, React Router และ service สำหรับเรียก API ด้วย fetch
- Node.js + Express: REST API, การตรวจข้อมูล, middleware ตรวจสิทธิ์, error handler และเรียก SQL
- PostgreSQL: ข้อมูลจริง เงื่อนไขข้อมูล ธุรกรรม และ SQL สรุปยอด
- ใช้ pg และ parameterized SQL เพื่อให้เห็นและฝึก SQL โดยตรง พร้อม SQL migrations ที่มีลำดับ ไม่เพิ่ม ORM ในรุ่นแรก
- ใช้ JavaScript แบบ ESM, CSS ธรรมดา และรูปแบบโค้ดสม่ำเสมอ ยังไม่เพิ่ม TypeScript หรือระบบจัดการ state ส่วนกลาง
- ระหว่างพัฒนาใช้ Vite proxy ให้ /api ไป Express; production ให้ Express ให้บริการ React ที่ build แล้วและ /api บน origin เดียวกัน
- โครงสร้างโค้ดที่เสนอเมื่ออนุมัติแบบแล้ว: client/, server/, db/migrations/, docs/, README.md ใน repo ใหม่แยกจากโปรเจกต์อื่น
- เวอร์ชันแพ็กเกจและเครื่องมือรันฐานข้อมูลในเครื่องให้ผู้ทำแผนตรวจจากสภาพเครื่องและเอกสารทางการก่อนติดตั้ง

## 6. ประสบการณ์ของพ่อ

มีเมนูหลักสามเมนูพร้อมชื่อภาษาไทย: เติมแก๊ส, ประวัติ, สรุป เปิดครั้งปกติที่หน้าเติมแก๊ส และไม่แสดงรายละเอียดทางเทคนิคในขั้นตอนบันทึก

### เติมแก๊ส

ลำดับช่อง: จำนวนเงิน (บาท), ปริมาณ (ลิตร), วันที่เติม (เริ่มจากวันนี้) จากนั้นส่วนรายละเอียดเพิ่มเติมสำหรับเลขไมล์ เติมเต็มถัง ปั๊ม และหมายเหตุ ช่องเลขใช้แป้นตัวเลขที่เหมาะสม จำนวนเงินและลิตรจำเป็นต้องมากกว่า 0 วันที่แก้ย้อนหลังได้

ราคา/ลิตรแสดงหลังมีค่าที่ถูกต้องทั้งสองช่อง ไม่ต้องกรอกซ้ำ วันที่ของแบบร่างที่กู้กลับมาต้องแสดงให้เห็นชัด พ่อแก้ก่อนส่งได้ ไม่เปลี่ยนวันที่ของแบบร่างโดยเงียบ ๆ

ปุ่มบันทึกปุ่มเดียวเด่น ระหว่างส่งปิดการกดซ้ำ สำเร็จหลัง API ยืนยันข้อมูลที่บันทึก พร้อมข้อความและเงิน/ลิตรสรุป ถ้าล้มเหลวคงฟอร์มและรหัสรายการเดิมไว้ให้ลองใหม่ ไม่มีการส่งเบื้องหลังเอง

### ประวัติและแก้ไข

วันที่และจำนวนเงินเด่น รองลงมาเป็นลิตร ราคา/ลิตร และเลขไมล์ถ้ามี กดรายการเพื่อดูรายละเอียดและแก้ไข เลือกเดือนด้วยตัวควบคุมที่อ่านง่าย เริ่มแสดงล่าสุด 20 รายการและมีปุ่มโหลดเพิ่ม

ผู้ใช้ยืนยันเพิ่มเติมว่าต้องแก้ไขข้อมูลที่บันทึกแล้วได้ จึงมีปุ่ม "แก้ไข" พร้อมชื่อชัดเจนในรายการประวัติ เปิดฟอร์มที่เติมค่าปัจจุบันให้ครบ แก้วันที่ เงิน ลิตร เลขไมล์ เต็มถัง ปั๊ม และหมายเหตุได้ แสดงหัวข้อ "แก้ไขรายการเติมแก๊ส" ปุ่ม "บันทึกการแก้ไข" และ "ยกเลิกการแก้ไข" บันทึกทับ id เดิม ไม่เพิ่มรายการใหม่ ยกเลิกแล้วข้อมูลเดิมต้องไม่เปลี่ยน

แก้ไขใช้กฎเดียวกับเพิ่มรายการ สำเร็จแล้วโหลดประวัติและสรุปใหม่ หากส่งไม่สำเร็จเก็บค่าที่กำลังแก้ไว้ให้ลองอีกครั้ง ลบอยู่ในหน้ารายละเอียด ไม่วางติดปุ่มบันทึก ต้องยืนยันพร้อมวันที่และจำนวนเงินที่จะลบ ลบสำเร็จแล้วปรับประวัติและสรุปจากผลเซิร์ฟเวอร์

### สรุป

เริ่มที่เดือนปัจจุบัน มีเงินรวม ลิตรรวม จำนวนครั้ง และราคาเฉลี่ยต่อหนึ่งลิตร = เงินรวม / ลิตรรวม ถ้าไม่มีข้อมูลแสดง 0 สำหรับยอดรวม และ "ยังไม่มีข้อมูล" สำหรับราคาเฉลี่ย ไม่ใช้ค่าเฉลี่ยของราคาทุกรายการ

### หลักการแสดงผล

ใช้แนว Accessible & Ethical จาก ui-ux-pro-max: ตัวอักษรไทยพื้นฐาน 18px ระยะบรรทัดประมาณ 1.6, ปุ่มหลักสูงอย่างน้อย 52px, จุดกดอย่างน้อย 44x44px และเว้น 8px ขึ้นไป ใช้พื้นทึบ สีอ่านชัด ไม่ใช้กระจกโปร่งหรือการเคลื่อนไหวตกแต่ง

ใช้ชุดตัวอักษร system ที่แสดงภาษาไทยได้ก่อน เพิ่มฟอนต์ภาษาไทยได้ภายหลังเมื่อจำเป็น ข้อความปกติต้องได้ contrast อย่างน้อย 4.5:1 มี label จริง focus ที่เห็นชัด และไม่ใช้สีสื่อความหมายเพียงอย่างเดียว รองรับ zoom, keyboard และหน้าจอแคบ 320px โดยไม่เลื่อนแนวนอน คีย์บอร์ดมือถือไม่ควรบังปุ่มหลักโดยไม่มีทางเลื่อนถึง

ระบบค้นสกิลให้รูปแบบ landing page ที่ไม่ตรงกับแอปนี้ จึงใช้เฉพาะผล style ที่ตรงและหลัก UX ที่ตรวจสอบได้ รูปแบบเมนูและลำดับช่องเป็นข้อเสนอของผู้ออกแบบ

ภาพร่างประกอบเป็นข้อมูลตัวอย่างและการโต้ตอบในเครื่องเท่านั้น ไม่เชื่อม Backend และไม่ถือเป็นโค้ดผลิตภัณฑ์ที่อนุมัติแล้ว

## 7. ข้อมูลและกฎคำนวณ

ตาราง fuel_logs ใช้กับรถคันเดียว จึงยังไม่มี users หรือ vehicles

| ชื่อ | ชนิด / เงื่อนไข |
|---|---|
| id | UUID primary key สร้างจาก client ก่อนส่งครั้งแรก ใช้ซ้ำเมื่อ retry |
| filled_on | DATE, required, ไม่เกินวันปัจจุบันตาม Asia/Bangkok |
| amount | NUMERIC(12,2), มากกว่า 0, รับทศนิยมไม่เกิน 2 หลัก |
| liters | NUMERIC(10,3), มากกว่า 0, รับทศนิยมไม่เกิน 3 หลัก |
| odometer | INTEGER nullable, 0 ถึง 9,999,999 กม. |
| full_tank | BOOLEAN default false |
| station | VARCHAR(120), optional, trim แล้วค่าว่างเป็น null |
| note | VARCHAR(500), optional, trim แล้วค่าว่างเป็น null |
| created_at / updated_at | TIMESTAMPTZ, เซิร์ฟเวอร์กำหนด |
| deleted_at | TIMESTAMPTZ nullable; ทุกการอ่านปกติตัดรายการที่ลบออก |
| version | INTEGER เริ่มที่ 1 เพิ่มเมื่อแก้ไขหรือลบ |

เพิ่ม index สำหรับการอ่าน active records ตาม filled_on DESC, created_at DESC, id DESC ใช้ลำดับเดียวกันใน pagination

API รับ/ส่ง amount และ liters เป็น decimal strings เช่น "500.00", "32.500" ตรวจค่าก่อนส่งลง NUMERIC ไม่ยอมให้ PostgreSQL ปัด precision เกินที่กำหนดโดยเงียบ ๆ SQL คำนวณและรวมยอดด้วย NUMERIC; frontend ใช้ค่าปัดเพื่อแสดงผลเท่านั้น ราคา/ลิตรปัดแสดง 2 ตำแหน่ง และไม่เก็บเป็นค่าที่กรอกเอง

filled_on ส่งเป็น YYYY-MM-DD (ค.ศ.) รูปแบบวันที่บนหน้าจอเป็นภาษาไทยและระบุปีให้ชัด การกรองเดือนใช้ DATE ตั้งแต่วันแรกถึงก่อนวันแรกของเดือนถัดไป ไม่ใช้ created_at เป็นวันเติม

เลขไมล์ไม่บังคับ ไม่ใช้ 0 แทนค่าที่หาย ถ้าขัดกับรายการก่อนหรือหลังตามวันที่ให้เตือนโดยไม่ห้ามบันทึก เพราะอาจกรอกย้อนหลังหรือแก้ข้อมูล การคำนวณอัตราสิ้นเปลืองยังไม่อยู่ในรุ่นแรก

## 8. สัญญา API

ทุก endpoint ที่แตะข้อมูลรถต้องตรวจ session; รายการตัวอย่าง Portfolio ต้องแยกจากข้อมูลพ่อ

| Endpoint | การทำงาน |
|---|---|
| POST /api/access/setup | รับ setup token ใน JSON body ออก cookie หลังตรวจ token; จำกัดอัตราการเรียก |
| GET /api/access/status | บอกว่าสิทธิ์เครื่องยังใช้ได้หรือไม่ ไม่เปิดเผย token |
| GET /api/fuel-logs?month=YYYY-MM&limit=20&cursor=... | month optional; limit 1–100; ตอบ items, nextCursor |
| GET /api/fuel-logs/:id | อ่าน active record เดียว |
| POST /api/fuel-logs | เพิ่มรายการแบบ idempotent ตาม id ที่ client สร้าง |
| PATCH /api/fuel-logs/:id | แก้ค่าที่อนุญาต พร้อม version ของข้อมูลที่กำลังแก้ |
| DELETE /api/fuel-logs/:id | soft delete โดยส่ง version ผ่าน If-Match header |
| GET /api/summary?month=YYYY-MM | รวม amount, liters, count, weighted average ของ active records |
| GET /api/health | เช็กว่าเซิร์ฟเวอร์ตอบได้ ไม่แสดง credentials หรือข้อมูลพ่อ |

ตอบข้อมูลปกติเป็น JSON; ข้อผิดพลาดใช้ { error: { code, message, fields? } } ให้ frontend แปลเป็นข้อความไทยที่ทำอะไรต่อได้ Status หลัก: 201 เพิ่มใหม่, 200 ส่งซ้ำที่สำเร็จแล้ว/อ่าน/แก้ไข, 204 ลบ, 400 รูปแบบคำขอผิด, 401 ไม่มีสิทธิ์, 404 ไม่พบ, 409 ข้อมูลขัดแย้ง, 422 ค่าในช่องไม่ผ่าน, 429 เรียกถี่, 500 ข้อผิดพลาดภายในพร้อม request id โดยไม่ส่ง stack trace

POST id เดิมและ payload เดิมให้คืนรายการที่มีอยู่โดยไม่เพิ่มใหม่ เปรียบเทียบกับ payload ตอนสร้างที่ normalize แล้ว ไม่ใช่ค่าปัจจุบันที่อาจแก้ไป; เก็บ create_payload JSONB หรือข้อมูลต้นฉบับที่เทียบได้ในตารางเดียวกัน หาก id เดิมแต่ payload ต่างกันหรือรายการถูกลบแล้วให้ 409 ไม่สร้างกลับใหม่

PATCH ตรวจ version แบบ atomic ไม่ตรงให้ 409 และเก็บค่าที่กรอกไว้เพื่อ reload แล้วแก้ใหม่ DELETE ซ้ำของรายการที่ลบแล้วตอบ 204; ถ้ารายการยังอยู่แต่ version ไม่ตรงตอบ 409 การเขียนสำเร็จต้อง commit ก่อนตอบกลับ

Frontend เก็บ draft และ id ลง localStorage หลังมีการเปลี่ยนค่า เฉพาะแบบร่าง ไม่เก็บ credentials ถ้าส่งสำเร็จล้าง draft และ id; ถ้าคำตอบหายให้ส่งซ้ำ id เดิม ถ้าพ่อเปลี่ยน draft หลังผลส่งไม่แน่ชัด ให้ตรวจ id เดิมกับเซิร์ฟเวอร์ก่อนเริ่มรายการใหม่เพื่อไม่สร้างรายการซ้ำ

## 9. เข้าใช้โดยพ่อไม่ต้องล็อกอิน

นี่เป็นข้อเสนอทางเทคนิคของผู้ออกแบบ เพื่อรองรับความต้องการที่ผู้ใช้ระบุว่าไม่ต้องล็อกอิน: ผู้ใช้เปิดลิงก์ตั้งค่าลับบนมือถือพ่อครั้งแรก จากนั้นระบบจำเครื่องด้วย cookie

- Setup token สุ่มอย่างน้อย 32 bytes และคาดเดาไม่ได้ ผู้ใช้เก็บลิงก์สำรองเป็นส่วนตัว Backend เก็บเฉพาะ SHA-256 hash ใน environment configuration
- ลิงก์ตั้งค่าใส่ token ใน fragment เช่น /#access=...; หน้าเว็บอ่านแล้วล้าง fragment ออกจาก URL ทันที ก่อนนำส่งใน JSON body ผ่าน HTTPS ไม่ใส่ใน query string และไม่บันทึกลง log/analytics/localStorage
- POST setup ตรวจ token แบบ constant-time และสร้าง session token สุ่มใหม่ เก็บเฉพาะ hash ใน device_sessions พร้อม created_at, expires_at, revoked_at และ id
- Production cookie: __Host-fuel_session, Secure, HttpOnly, SameSite=Strict, Path=/ อายุ 180 วันแบบเลื่อนวันเมื่อใช้งานอย่างถูกต้อง สามารถถูกเบราว์เซอร์ล้างหรือหมดอายุได้ ไม่สัญญาว่าจำเครื่องถาวร
- เปิดจากไอคอน URL ปกติใน browser context เดียวกับที่ตั้งค่า เมื่อเปลี่ยนเครื่อง ล้างข้อมูล เปิด private mode หรือ context ของไอคอนแยกสิทธิ์ ผู้ใช้ตั้งค่าลิงก์ให้ใหม่ ไม่แสดงหน้าสมัครสมาชิกหรือให้พ่อตั้งรหัส
- ไม่บังคับติดตั้ง PWA; ทดสอบวิธีเพิ่ม shortcut กับมือถือจริงก่อนเลือกวิธีติดตั้ง หาก shortcut แยก cookie ต้องตั้งค่าใน context นั้น
- ถ้าไม่มีสิทธิ์ หน้าจอภาษาไทยแจ้งให้ติดต่อผู้ใช้เพื่อตั้งค่าใหม่ และไม่แสดงข้อมูลรถ
- ผู้ใช้เพิกถอน sessions ทั้งหมดและเปลี่ยน setup token ผ่านเครื่องมือดูแลที่ไม่เปิดเป็น public API ไม่มี dashboard จัดการผู้ใช้ในรุ่นแรก
- ทุกการเขียน รวม setup ต้องเป็น same-origin ตรวจ Origin และ Content-Type JSON; ไม่เปิด CORS ให้ origin อื่น ใช้ rate limit, request body limit และไม่ cache คำตอบข้อมูลส่วนตัว
- ใครได้ setup link ยังคงตั้งค่าสิทธิ์เข้าใช้ได้จนถูกเปลี่ยน จึงถือเป็นกุญแจ ผู้ใช้ต้องเก็บเป็นส่วนตัว การเพิกถอนต้องทำทั้ง setup token และ sessions เมื่อสงสัยว่าลิงก์รั่ว

พ่อไม่ต้องเห็นขั้นตอนทางเทคนิคเหล่านี้ในระหว่างบันทึกประจำวัน

## 10. การทดสอบและเกณฑ์รับงาน

ทดสอบที่ช่วยป้องกันข้อผิดพลาดจริง: validation, precision ทศนิยม, เปลี่ยนเดือน/ขอบเขตวัน, SQL รวมยอด, idempotent create รวมกรณี response หาย, แก้ version เก่า, soft-delete แล้วไม่ติดยอด, และทุก data endpoint ปฏิเสธเมื่อไม่มีสิทธิ์

ทดสอบ API กับ PostgreSQL สำหรับทดสอบโดยเฉพาะ ห้ามใช้ข้อมูลพ่อ ทดสอบ UI เส้นทางเพิ่ม/แก้/ลบ รวม network error ที่เก็บ draft และไม่แสดงสำเร็จผิด ตรวจมือถือจริงอย่างน้อยหนึ่งเครื่อง และ responsive ที่ 320, 375, 768, 1024px พร้อม keyboard/zoom

ก่อนเริ่มให้พ่อใช้จริงต้องทำได้ครบ:

1. ตั้งค่าเครื่องครั้งแรก แล้วเปิดใหม่จากไอคอนโดยไม่มีการกรอกบัญชี
2. บันทึก 500 บาท 32.5 ลิตร เห็นข้อมูลเดิมหลังปิดและเปิดเว็บใหม่
3. ส่ง id เดิมซ้ำแล้วฐานข้อมูลมีเพียงหนึ่งรายการ
4. เน็ตหลุดหรือเซิร์ฟเวอร์ผิดพลาดแล้วไม่สูญเสีย draft; ส่งใหม่ไม่เพิ่มซ้ำ
5. แก้และลบแล้วประวัติกับสรุปเดือนตรงกัน ไม่มีเดือนว่างหารด้วยศูนย์
6. เบราว์เซอร์ใหม่ที่ไม่ได้ตั้งค่าอ่านหรือแก้ข้อมูลพ่อผ่าน API ไม่ได้
7. กู้ฐานข้อมูลสำรองลง test database ได้อย่างน้อยหนึ่งครั้ง
8. ให้พ่อลองบันทึกเอง สังเกตจุดติดขัด และแก้สิ่งที่ขัดขวางการใช้งาน เป้าหมายเบื้องต้นคือลองกรอกรายการปกติภายในประมาณหนึ่งนาทีเมื่อมีตัวเลขพร้อม ตัวเลขนี้เป็นเป้าทดลองของผู้ออกแบบ ไม่ใช่ผลที่วัดแล้ว

## 11. การเผยแพร่ สำรองข้อมูล และ Portfolio

แผนการติดตั้งที่เสนอคือ Node host หนึ่งตัวให้บริการทั้งเว็บและ API พร้อม managed PostgreSQL ผ่าน HTTPS ชื่อบริการ/ค่าใช้จ่ายยังไม่ตัดสินในแบบนี้ ผู้ทำแผนต้องเสนอทางที่เหมาะกับเครื่องและงบก่อนใช้บริการเสียเงิน

Secrets เก็บใน environment ของ server ไม่ใส่ Vite variables ที่ถูก bundle ลง browser มี .env.example เฉพาะชื่อและค่าจำลอง, .gitignore และ log ที่ไม่เก็บ tokens/cookies มี health endpoint และ request ids ช่วยแก้ปัญหา

รุ่นแรกให้ผู้ใช้สำรองผ่าน pg_dump อย่างน้อยสัปดาห์ละครั้งและก่อน migration ที่เปลี่ยนข้อมูล เก็บนอก repo ในที่ส่วนตัว และตรวจ restore ไปยัง test database README ระบุว่าต้องให้ผู้ดูแลทำขั้นตอนนี้ ระบบสำรองอัตโนมัติค่อยพิจารณาตาม hosting ที่เลือก

Portfolio ใช้ screenshots/วิดีโอหรือชุดข้อมูลจำลองที่ระบุชัด ไม่เผยลิงก์ตั้งค่าหรือข้อมูลพ่อ README มีปัญหาของผู้ใช้จริง ขอบเขต โครงสร้างระบบ schema API วิธีรัน migration/test/deploy การสำรอง/กู้คืน ข้อจำกัด และสิ่งที่ปรับหลังทดลอง

บันทึกบทบาท AI ตามจริง รวมส่วนที่ผู้ใช้เข้าใจ ทดลอง แก้ และตัดสินใจเอง ข้อความ CV ใช้เฉพาะสิ่งที่ทำแล้ว ไม่มีตัวเลขผู้ใช้ ผลประหยัดเวลา หรือความสำเร็จที่ยังไม่ได้วัด

## 12. ขนาดงานและลำดับเป้าหมาย

เป็นหนึ่งโปรเจกต์ Full-stack ขนาดเล็ก แยกเป้าหมายการเรียนรู้:

1. React form และประวัติข้อมูลจำลอง พร้อมทบทวน JavaScript ที่ใช้
2. SQL migration และ API เพิ่ม/อ่านข้อมูลจริง
3. เชื่อม React → API → PostgreSQL พร้อม validation, retry และ draft
4. แก้ไข/ลบ สรุปเดือน และทดสอบความถูกต้อง
5. ตั้งค่าการเข้าถึง เผยแพร่ ทดลองกับพ่อ และจัด Portfolio

การพัฒนาสิทธิ์อาจจัดเตรียม local-only ระหว่างเรียน แต่ห้ามเปิดข้อมูลจริงบนอินเทอร์เน็ตก่อนติดตั้งและตรวจสิทธิ์แล้ว ช่วงเวลาประเมินเดิม 3–6 สัปดาห์ที่ผู้ใช้ศึกษา/ทดลองราว 10 ชั่วโมงต่อสัปดาห์เป็นกรอบประมาณการสำหรับ AI ช่วยลงมือ ไม่ใช่กำหนดส่ง ต้องประเมินใหม่หลังตรวจเครื่องและทดลองช่วงแรก

## 13. สิ่งที่ให้ผู้ทำแผนตัดสิน และสิ่งที่ยังรออนุมัติ

ผู้ทำแผนเลือกเวอร์ชันที่รองรับ เครื่องมือ migrations/test, โครงสร้าง component, กลไก rate limiting, วิธีรัน PostgreSQL ในเครื่อง, การจัดไฟล์ CSS และโค้ด cookie/session โดยรักษาพฤติกรรมในแบบนี้ ใช้ไลบรารีที่ดูแลอยู่เมื่อเหมาะสมแทนการประดิษฐ์กลไกเข้ารหัสเอง

ก่อน deploy จริงต้องตรวจระบบมือถือ/เบราว์เซอร์พ่อและวิธี shortcut รวมถึง hosting และงบ รายละเอียดเหล่านี้ไม่ขวางการเขียนแผนหรือพัฒนาในเครื่อง

ยังรอผู้ใช้ตรวจแบบ โดยเฉพาะเลขไมล์ไม่บังคับ รูปแบบหน้าจอ และการจำสิทธิ์เครื่องแบบตั้งค่าครั้งแรก เมื่อแบบได้รับอนุมัติให้ใช้ writing-plans เพื่อเขียนแผนลงมือทำ ก่อนเริ่ม scaffold, ติดตั้ง dependencies หรือเขียนโค้ดผลิตภัณฑ์

ผู้ใช้สร้างโฟลเดอร์ D:/Personal_Project/lpg-fuel-log และย้าย docs ของโครงการมาไว้ภายในแล้ว โฟลเดอร์นี้ยังไม่ใช่ Git repository จึงยังไม่ได้ commit ให้เก็บเอกสารที่มีอยู่และสร้าง repo ที่โฟลเดอร์โครงการหลังอนุมัติการลงมือทำ โดยไม่ต้องย้ายหรือคัดลอก docs ซ้ำ
